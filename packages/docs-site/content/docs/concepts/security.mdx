A memory product holds the most compounding thing you have: what you and
your agents know. Our security posture follows one principle — **every
protection below is enforced by code you can read, not by policy prose**.
This page only describes mechanisms that are shipped and testable in the
open-source server. If it isn't listed here, we don't claim it.

## Owner isolation, four layers deep

Every read of memories or chunks passes through layered, fail-closed
enforcement:

1. **One SQL source of truth** — all read-path access predicates are
   generated by a single scope builder (`VisibilityScope.SQLFilter`),
   unit-tested in isolation. Handlers cannot hand-roll a broader query.
2. **Fail-closed chunk access** — the chunk search layer has explicit
   access modes; the `default` branch denies, and strict scopes with an
   empty hub list return an error instead of falling back to a wider
   search.
3. **Parent-ownership checks** — chunk reads verify the parent memory's
   ownership before returning content.
4. **CI-enforced rules** — an AST-level checker runs in CI and fails the
   build if agent-tool code calls the store in a shape that could bypass
   scoping (including the "former hub member reaches old content" case).

Cross-tenant boundaries are covered by integration tests that assert a
member of one hub can never read another hub's content — including
adversarial cases found in external review and locked in as regression
tests.

## Identity comes from credentials, never from payloads

Who wrote a memory is security metadata, so Memax refuses to let it be
self-reported:

- Agent identity is carried by the **credential** — the OAuth grant's
  identity is frozen at authorization time; API keys are pinned to an
  agent on first use (trust-on-first-use) and cannot be re-claimed.
- A payload claim that **conflicts** with the credential fails the write
  outright rather than being silently reinterpreted — the same posture as
  immutable-field semantics in Google AIP-203 and AWS STS
  `SourceIdentity`.
- The MCP specification itself warns that client-reported identity
  ("clientInfo") must not drive security decisions. We agree: our MCP
  tool schemas don't even advertise an identity field to models.

## Synthesis is verified, not trusted

Memax's background intelligence (dreams, pulse cards) makes claims about
your knowledge — so every claim is checked against the store before it
ships:

- Every card citation is **re-read from the database** and its hub
  verified; a single fabricated quote discards the entire card.
- Attribution on team cards comes from stored authorship, never from
  model output; cards whose receipts don't match their claim are dropped
  and the drop is logged.

An empty board is an acceptable result. A hallucinated insight is not.

## Credentials are rejected at the door

Memories are chunked, embedded, and recalled **verbatim** across every
agent you connect — which means a credential that enters a memory becomes
a replay device. So the push paths (REST, SDK, CLI, MCP) detect
high-confidence credential shapes — vendor API keys, private-key blocks,
JWTs, credential assignments — and **reject the write** with an error
that names the pattern and tells you what to do instead.

<Callout type="info">
  Memax deliberately does **not** offer encrypted credential storage. A
  memory pipeline must read content to embed and recall it, which is
  architecturally incompatible with the zero-knowledge model real secret
  managers use. Keep secrets in a secret manager; push references, not
  values.
</Callout>

The detection is deliberately scoped to credentials only: git SHAs,
localhost URLs, and internal IPs are everyday developer memory content
and are never blocked.

## Transport, storage, and sessions

- TLS everywhere in transit; storage encryption at rest via the managed
  database layer.
- Access tokens expire in 1 hour; a session lasts 30 days. Permissions
  resolve server-side on every request — revoking a key or an agent's
  authorization takes effect immediately, not at token expiry.
- Refresh tokens are stored only as a hash and replaced on every refresh.
  A replaced refresh token used again signs the whole session out, since
  it means someone else holds a copy.
- Every sign-in is a session you can see and sign out (`GET
  /v2/sessions`, `memax sessions`): signing one out ends its refresh
  token at once, and its last access token within the hour. `memax
  logout` signs the CLI's session out on the server.
- On the web app, the session lives in HttpOnly, `SameSite=Strict`
  cookies that only the web app's server reads; page scripts never see a
  token.
- Admin surfaces use a separate auth model and are never exposed in the
  published SDK.

## Sub-processors

Some features send memory text to outside services. These are the ones
the reviewed record (Memax V2) uses, each only while the feature is on:

| Sub-processor | What it receives | Used for | Retention |
| ------------- | ---------------- | -------- | --------- |
| [OpenRouter](https://openrouter.ai) | A proposal and the memories it's compared with; an Ask question and the kept memories it may cite | Routing each model call to one of the hosts below | Zero data retention: every call sets `provider.zdr`, so OpenRouter refuses any host that retains prompts |
| Together AI, Baseten, CoreWeave, DeepInfra (through OpenRouter, in that order) | The same, for DeepSeek V4.1 Flash | The judge's first pass, and Ask's answers | Zero-retention endpoints only, at fp8 precision or better. Never DeepSeek's own API |
| Amazon Bedrock, then Google Vertex AI (through OpenRouter) | The same, for Claude Haiku 4.5 | The judge's fallback, when the first pass gives no usable answer | Zero-retention endpoints only |
| Google Vertex AI (through OpenRouter) | A proposal and the decisions in force it touches, for Claude Sonnet 5.5 | Confirming any verdict about a decision in force | Zero-retention endpoints only |
| [Voyage AI](https://www.voyageai.com) | Each kept memory and proposal, and each search query | Embeddings for search, and reranking | Voyage stores API inputs for training unless the account opts out, which gives zero-day retention. Treat embeddings as held under Voyage's terms until we publish that the opt-out is on |

Each model call names its hosts as an allowlist (OpenRouter's
`provider.only`) and the precisions they may run
(`provider.quantizations`), so a host that isn't listed here never
serves it, even as a fallback. The lists are server configuration
(`JUDGE_PROVIDERS`, `ASK_PROVIDERS` and the `*_MIN_QUANTIZATION`
settings), and a self-hosted server can change them.

<Callout type="warn">
  The original Memax features (memory processing, dreams, and the first
  Ask) still call OpenRouter without this routing, and rerank with Cohere
  when it's configured. They get bug fixes only and are replaced by the
  reviewed record.
</Callout>

## What we don't claim (yet)

Honesty about limits is part of the posture:

- **No tamper-evident audit chain yet** — access logging exists;
  hash-chained, externally-anchored audit is designed but deliberately
  not shipped pre-launch.
- **No per-memory sharing circles yet** — access is hub-membership based
  today; finer-grained disclosure (audience circles) is a published
  design direction, not a shipped feature.
- **The `boundary` field is not an access-control mechanism** — see
  [Access &amp; visibility](/docs/concepts/boundaries) for the real model.
